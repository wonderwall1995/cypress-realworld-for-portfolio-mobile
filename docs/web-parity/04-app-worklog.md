# 앱 수정 작업 기록

코덱스 보고서(01~03)를 앱 코드와 웹 소스에 대조한 결과와, 그에 따라 앱을 고치는 순서다. 앱 수정이 끝난 뒤 앱의 자동화 테스트(Appium, WDIO)를 쓴다. 테스트 설계는 사용자가 한다.

- 시작: 2026-11-23. 앱 `main`의 `cbc9294`, 앱 내부 자동 테스트 379개 통과.
- 웹 기준: 보고서는 `58ed97b`, 이 기록은 그 뒤의 `3185fe9`까지 본다. 웹 저장소는 읽기만 한다.
- 진행 방식: 한 땀마다 **문서(할 일) → 코딩 → 문서(결과)**. 코드를 일부러 되돌려 테스트가 실패하는지 확인한 것만 "되돌림 확인"이라고 적는다.
- 확인 수준: `자동`은 가짜 서버를 쓰는 앱 내부 테스트, `에뮬레이터`는 실제 서버에 붙인 Android 에뮬레이터, `미확인`은 실행하지 못한 것이다.

## 웹에 요청할 것

앱에서 고칠 수 없는 것이다. 사용자가 웹 쪽에 전달한다.

1. (P0) 입금과 이체의 요청 식별자. 같은 식별자가 다시 오면 처음 결과를 돌려준다. 지금은 응답이 사라진 뒤 다시 보내면 두 번 처리될 수 있다. 앱은 "결과를 알 수 없음"으로 안내할 뿐 막지 못한다.
2. (P1) 이체의 `privacyLevel` 검사가 아직 `contacts`를 받는다(`DefaultPrivacyLevelValues`). 설정과 같은 두 값으로 맞춘다.
3. (P1) 오류에 안정된 `code`를 붙인다. 지금은 앱과 웹이 영문 문장의 일부로 판단한다.
4. (P1) 계좌 60개 제한과 삭제의 동시 요청 확인.
5. (P1) 가입할 때 이미 있는 ID를 409로 거절한다. 지금은 DB의 고유 조건에 걸려 500이 되어, 앱과 웹이 이유를 알 수 없다.

## 기록

### 땀 1. 오류와 로그인 (완료)

- 실패를 다섯 가지로 나눴다: 보내지 못함, 답을 못 받음, 거절(4xx), 서버 장애(5xx), 읽을 수 없는 답. 뒤의 셋 중 "답을 못 받음, 서버 장애, 읽을 수 없는 답"은 쓰기 요청에서 "결과 불명"이다.
- 422의 `msg`, `param`을 읽어 어느 칸인지 한국어로 말한다. 칸의 규칙은 폼이 먼저 검사하므로 서버의 422는 폼 위 안내로 보인다.
- 5xx와 HTML 본문은 화면에 보이지 않는다. 4xx에서 표에 없는 서버 이유는 웹과 같이 괄호로 덧붙인다(보고서는 모두 숨기자고 했으나 웹과 맞췄다).
- 보호 API가 401이면 로그인 화면으로 가고 "로그인이 만료되었습니다. 다시 로그인해 주세요."를 보인다. 열려 있던 입금 창과 비밀번호 창은 닫히고, 다시 로그인해도 그 요청을 보내지 않는다. 로그인 실패의 401과 구분한다.
- 앱을 열 때 서버에 닿지 않으면 로그아웃하지 않고 "서버에 연결할 수 없습니다."와 "연결 다시 확인"을 보인다.
- 이전 사용자의 늦은 응답(계좌, 입출금 내역)과 늦은 401을 버린다. 계좌 다시 읽기가 실패해도 이전 목록을 지키고, "계좌 0개"로 보이지 않는다.
- 로그인과 가입 폼은 처리 중의 두 번째 제출을 무시한다.
- 새 식별자: `offline`, `offline-retry`.
- 확인: 자동 399개 통과. 되돌림 확인 9개(늦은 응답, 늦은 401, 로그인 401, 401 알림, checkAuth null, 오프라인, 5xx, 시간 초과, 403 구분).

### 땀 2. 입금과 이체 (할 일)

1. 입금 처리 중에는 취소, 바깥 탭, 뒤로 가기를 막고 "처리 중입니다"를 보인다. 이체 확인 창의 뒤로 가기도 같다.
2. 이체의 403을 비밀번호 오류와 계좌 권한 오류로 나눈다. 계좌 문제(404, 403, 삭제됨, 잔액 부족)는 창을 닫지 않고 이유를 보이고 "계좌 다시 선택"을 준다. 계좌 목록을 다시 읽는다.
3. 비밀번호 확인 단계의 실패와 이체 단계의 실패를 구분한다. 비밀번호 확인만 실패하면 이체는 보내지 않은 것이다.
4. 결과 불명이면 다시 보내는 버튼을 끄고 "내역 확인"을 준다. 자동으로 다시 보내지 않는다.
5. 서버가 승인한 뒤 잔액을 다시 읽지 못하면 "처리는 완료됐지만 최신 잔액을 불러오지 못했습니다"와 다시 읽기를 보인다. 승인된 거래를 실패로 되돌리지 않는다.
6. 상대에게 계좌가 없으면 상대를 다시 고를 수 있다.

- 결과:
  - 입금 창과 이체 확인 창은 전송 중에 취소, 바깥 탭, 뒤로 가기로 닫히지 않고 "처리 중입니다."를 보인다. 전송 전에는 닫힌다. 닫을 때 다른 화면을 닫지 않는다.
  - 결과 불명이면 "응답을 받지 못해 처리 결과를 확인할 수 없습니다."를 보이고 보내기 버튼 대신 "내역 확인"을 준다. 키보드의 완료 키로도 다시 보내지 않는다.
  - 보내지 못한 것(연결 실패)은 결과 불명이 아니므로 다시 시도할 수 있다.
  - 비밀번호 확인 실패와 이체 실패를 나눴다. 403은 서버가 비밀번호라고 말할 때만 비밀번호 오류다. 계좌가 이유이면 "계좌 다시 선택"을 주고 양쪽 계좌를 다시 읽는다. 입력한 금액과 메모는 남는다.
  - 다른 곳에서 삭제된 계좌가 선택된 채로 남아 앱이 멈출 수 있던 문제를 고쳤다(보고서에 없던 것).
  - 승인 뒤 잔액 읽기는 따로 다룬다. 실패하면 "처리는 완료됐지만 최신 잔액을 불러오지 못했습니다."와 다시 읽기만 준다. 이 상태는 `money_status.dart` 한 곳에서 관리한다(땀 6의 부분 실패도 같은 곳).
  - 내 계좌를 못 읽었을 때와 계좌가 없을 때를 구분하고, 상대에게 계좌가 없으면 "상대 다시 선택"을 준다.
- 새 식별자: `bank-transfer-busy`, `bank-transfer-check-history`, `transfer-confirm-busy`, `transfer-confirm-reselect`, `transfer-confirm-check-history`, `transaction-create-my-accounts-error`, `transaction-create-no-account`, `transaction-create-make-account`, `transaction-create-change-receiver`, `transaction-create-refresh-failed`, `transaction-create-refresh`.
- 확인: 자동 414개 통과. 되돌림 확인 12개. 처음에 하나(삭제된 계좌 선택)가 잡히지 않아, 거절 뒤 취소해도 계좌를 다시 읽도록 고치고 테스트를 더했다.

### 땀 3. 은행 계좌 (할 일)

1. 강제 온보딩 화면을 없앤다. 계좌가 없어도 홈, 설정, 알림, 로그아웃을 쓴다. 입금과 이체를 누르면 필요할 때 만들기로 간다.
2. 계좌가 없을 때만 은행 계좌 메뉴를 노랗게 한다. 화면 글자는 넣지 않는다. 못 읽은 것은 "없음"이 아니다.
3. 계좌 60개이면 만들기를 끄고 안내한다.
4. 만들기와 삭제의 연속 제출을 막는다. 만드는 중에 화면을 나가도 다른 화면이 닫히지 않는다.
5. 삭제가 거절되면 목록을 다시 읽는다. 다른 사용자에게 오류 문구가 남지 않는다.
6. 조회 실패 때 앱이 몰래 여러 번 다시 묻는 것(Riverpod 기본값)을 끈다. 화면의 "다시 시도"가 있다.

- 결과:
  - 강제 온보딩 화면과 코드를 지웠다. 계좌가 없어도 모든 탭, 설정, 로그아웃을 쓴다. 입금 창과 이체 화면이 필요할 때 "은행 계좌 만들기"로 이끌고, 만든 뒤 원래 화면으로 돌아온다.
  - 계좌가 없으면 은행 계좌 메뉴가 노란색(웹과 같은 색)이다. 화면 글자는 없고 스크린리더 안내만 있다. 목록을 못 읽은 것은 노란색이 아니다.
  - 계좌 60개이면 만들기가 꺼지고 "은행 계좌는 최대 60개까지 만들 수 있습니다."를 보인다.
  - 만들기의 두 번째 제출을 무시한다. 만드는 중에 뒤로 가도 다른 화면(더보기 등)이 닫히지 않는다(보고서에 없던 것).
  - 만들기와 삭제가 실패하면 목록을 다시 읽는다. 은행 계좌 탭을 다시 열면 이전 오류 문구가 사라진다.
  - 조회 실패 뒤 앱이 몰래 다시 묻던 것(최대 10번)을 껐다.
- 없어진 식별자: `user-onboarding-*`. 새 식별자: `bankaccount-limit`, `sidenav-bankaccounts-warning`(화면 테스트 전용 키).
- 확인: 자동 421개 통과. 되돌림 확인 11개.

## 땀 10. 코덱스의 회신 반영

회신(웹 저장소의 Codex, `to.mobile.app.md`)을 앱 코드와 대조했다. 이미 된 것과 서버가 먼저인 것은 빼고 앱이 지금 할 수 있는 것만 한다.

할 일:

1. **결과 불명 뒤 다시 보내기.** 결과 불명인 입금이나 이체를 닫으면 경고 없이 다시 보낼 수 있었다. 결과를 확인하지 못한 시도가 있으면 같은 종류를 보내기 전에 묻는다. 확인 창이 아니라 그 시도에 붙어 있어, 창을 닫거나 다른 화면에 다녀와도 남는다. 앱을 끄면 사라진다(서버의 요청 식별자가 있어야 완전해진다).
2. **인증서 오류.** Dio는 이 오류를 요청을 보낸 뒤에 판정한다. "보내지 못함"에서 "답을 못 받음"으로 옮긴다. 연결 오류와 연결 시간 초과는 Dio가 연결 단계에서만 내므로 "보내지 못함"이 맞다(Dio 5.9.2 `io_adapter.dart`에서 확인).
3. **알림 이력.** 웹처럼 읽은 알림을 흐리게 남기고 배지는 읽지 않은 것만 센다. `GET /notifications?include=read`를 쓰되, 옵션을 모르는 서버가 읽지 않은 것만 줘도 동작한다. 웹은 `be78311`로 커밋했다.
4. 이체 화면의 제목을 "새 거래"에서 "이체"로, 알림의 "읽음" 버튼을 웹과 같은 "확인"으로 한다.

## 땀 11. 서버의 새 응답

서버가 앱의 편지를 받아 고친 것(웹 저장소의 커밋 전 변경) 가운데 앱의 안내가 틀려지는 것만 맞춘다. 예전 서버에서도 동작해야 한다.

할 일:

1. 가입 409: "이미 사용 중인 사용자 ID입니다" (웹과 같은 문장)
2. 비밀번호 429(10번 틀림): "비밀번호를 여러 번 틀렸습니다. 10분 뒤에 다시 시도하세요" (웹과 같은 문장). 확인 단계와 이체 단계 모두. "계좌 다시 선택"은 주지 않는다.
3. 가입 500: 새 서버는 이미 있는 ID에 409를 주므로 500은 다른 이유다. 이유를 추정하는 안내는 예전 서버(JSON이 아닌 500)에만 남긴다.
4. 그 밖의 429(배포 프록시의 로그인, 가입 제한, HTML): "요청이 많습니다. 잠시 뒤 다시 시도하세요"

바꿀 것이 없는 것: 동시 요청의 400(계좌를 다시 읽는다), 알림 읽음의 404(목록을 다시 읽는다), 이체의 contacts 422(앱은 두 값만 보낸다), 쿠키의 SameSite와 Secure.

결과:

- 네 가지를 넣었다. 가입 409는 문구가 아니라 상태 코드로만 판단한다(서버의 영문 문장은 약속이 아니다). 비밀번호 429는 문구로 구분하고, 문구가 바뀌면 "요청이 많습니다"로 안내한다. 영문은 어느 경우에도 보이지 않는다.
- 예전 서버(HTML 500)에서는 지금까지의 안내가 그대로 나온다.
- 확인: 자동 474개 통과. 되돌림 확인 8개 모두 잡힘.
- 에뮬레이터와 개발 서버(서버의 커밋 전 변경이 켜져 있음): 이미 있는 ID의 가입, 비밀번호를 10번 틀린 뒤 맞는 비밀번호로 이체(돈이 움직이지 않음)를 확인했고 임시 계정은 지웠다. 배포 프록시의 429는 자동 테스트로만 확인했다.

서버의 변경은 아직 커밋과 배포 전이다. 비밀번호 횟수 제한은 사용자가 빼기로 했다(땀 12).

## 땀 13. 요청 흔적 정리, 데모 안내, 쿠키 저장

결정(2026-11-23): 아래 세 가지를 한다. GitHub Actions 자동 확인은 하지 않는다(Drop). 패키지 올리기, iOS, 하이브리드 화면은 Backlog로 둔다. 배포 서버, 실제 폰, push는 사용자가 나중에 확인한다. 서버의 일은 새 문서로 전한다.

할 일:

1. 없어진 "요청" 기능의 흔적(모델, 문구, 알림 종류, 테스트, 가짜 서버)을 지운다. 서버로 확인한 것: `requestStatus` 칸 없음, 모든 거래가 `complete`, `requested` 알림 0건. "결제 부족분" 자동 출금도 없어졌다. 지금 서버는 입금에도 `transactionId`를 넣으므로 그 값으로 자동 출금을 알아보던 규칙은 틀렸다.
2. 아이디, 비밀번호, 이름, 이메일, 전화번호, 계좌를 입력하는 모든 화면과 남에게 보이는 글(메모, 댓글)에 "실제 개인 정보를 넣지 말고 지어낸 정보를 넣어 달라"는 안내를 둔다. 화면을 가리거나 작은 화면, 큰 글자, 키보드에서 넘치지 않아야 한다.
3. 로그인 쿠키를 평문 파일이 아니라 기기의 안전한 저장소(Android Keystore로 암호화)에 둔다. 예전 평문 파일은 지운다. 저장소를 읽지 못하면 앱이 죽지 않고 로그인 화면으로 간다.

결과:

- 요청과 자동 출금의 흔적을 모델, 문구, 알림 종류, 테스트, 가짜 서버에서 지웠다. 없어진 알림 종류가 오면 모르는 종류로 보고 보이지 않는다. 설정의 "새 거래의 기본 공개 범위"는 "새 이체의 기본 공개 범위"로 바꿨다.

- 안내를 시험하다가 예전부터 있던 흠 하나를 고쳤다. 작은 화면과 큰 글자에서 설정의 `@아이디` 줄이 넘쳤다.

- 확인: 자동 493개 통과. 되돌림 확인 18개 가운데 17개를 잡았다. 잡히지 않은 하나(망가진 쿠키를 다시 지움)는 패키지가 이미 하는 일이라 그 코드를 뺐다.

- release 빌드(코드 축소)에서 저장하고 다시 읽는 것을 임시 시작 파일로 확인했다(파일은 지웠다). release 앱으로 로그인하는 것은 https 서버가 필요해 확인하지 못했다.

서버의 일은 한 문서로 다시 모아 사용자에게 전했다(서버의 약점이 있어 커밋하지 않는다).

결과:

- 틀린 칸 가운데 맨 위의 것이 보이는 곳까지 화면이 움직인다. 이미 보이면 움직이지 않는다. 여섯 폼이 같은 함수(`checkForm`)를 쓴다.
- 확인: 자동 500개 통과. 되돌림 확인 7개 모두 잡힘(처음에는 화면이 커서 셋이 잡히지 않아 테스트를 작은 화면으로 바꿨다). 빈 목록의 식별자는 E2E 001이 에뮬레이터에서 본다. 칸이 움직이는 것은 자동 테스트로만 보았다.
- 보통 폰의 크기에서는 긴 폼도 대개 틀린 칸이 보인다. 키보드가 열렸거나 글자가 클 때 필요하다.

## 땀 16. 정식 실행의 끝맺음, 날짜를 한 글자씩 치는 테스트

할 일:

1. 번호를 받은 뒤의 어떤 오류에도 finish나 block을 보낸다. 기기 이름은 `rwa-mobile`. 잠금 파일(`pnpm-lock.yaml`, `pnpm-workspace.yaml`)이 바뀌어도 시험 코드가 바뀐 것으로 센다.
2. 웹에 있던 날짜 버그(두 자리 월이 01, 00으로 바뀜)를 앱의 테스트로 막는다.

결과:

- 가짜 번호 서버로 13가지 상황을 확인했다(버전 없음, 값 없음, 이름표 빠짐, 결과 파일 깨짐, 기기 이름 등). 실제 정식 실행은 하지 않았다.
- 앱에는 그 버그가 없었다. 날짜 다섯 개를 한 글자씩 치는 테스트를 더했고, 웹의 버그를 앱에 일부러 넣으면 잡힌다. 자동 505개 통과.
