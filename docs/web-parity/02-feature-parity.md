# 모바일 기능별 차이와 완료 조건

기본 기능 대부분은 이미 웹과 맞춰져 있다. 아래 완료 조건은 정상 경로에 예외 상황을 더한 제품 기준이다. “확인된 차이”는 소스에 드러난 동작이며, 비동기 경합이나 기기 동작은 별도 재현 항목이다.

## 인증과 사용자 전환

**현재:** 쿠키 복원, 로그인, 회원가입, 로컬 쿠키를 지우는 로그아웃이 있다. 계좌와 거래 목록은 사용자 ID 변경을 구독한다.

**확인된 차이:** `SessionController.restore()`는 통신 실패도 unauthenticated 상태로 바꾼다. `refreshUser()`는 checkAuth가 null이어도 기존 로그인 상태를 유지한다. 일반 API와 SSE에는 401 공통 종료 처리가 없다.

**보완:** 연결 실패는 쿠키를 지우지 않고 연결 복구 안내와 다시 확인을 제공한다. 로그인 만료가 확인되면 보호 화면을 닫고 로그인으로 이동한다. 이체 비밀번호를 폐기하고 계좌, 거래, 알림, 삭제 오류 등 사용자별 상태를 정리한다. 로그인 이후 이전 입금이나 이체를 자동으로 실행하지 않는다.

로그인, 회원가입, 계좌 생성 폼의 `_submit()`에는 입금·이체와 달리 시작 시점의 `_busy` 반환 검사가 없다. 버튼 비활성화 외에 키보드 완료와 같은 프레임의 연속 호출도 막는다. 인증 요청의 늦은 응답이 나중의 로그아웃이나 다른 로그인 결과를 덮지 않게 한다.

**완료 조건:** 서버 재시작 후 만료된 쿠키로 앱을 열거나 사용 중 401을 받으면 재로그인할 수 있다. 오프라인에서는 비밀번호 오류로 안내하지 않는다. A 계정의 조회가 늦게 끝난 뒤 B 계정으로 로그인해도 A의 데이터가 나타나지 않는다. 이 마지막 상황은 현재 코드에 요청 취소·세대 검사 없이 상태를 쓰는 경로가 있어 재현이 필요하다.

근거: M `core/session.dart`, `core/api_client.dart`, `features/bank_accounts/bank_accounts_controller.dart`, `features/notifications/notifications_controller.dart`.

## 계좌 없는 사용자와 은행 계좌

**현재:** 계좌 생성과 삭제는 서버 승인을 기다린다. visible=false는 숨기고, 잔액이 있는 계좌는 삭제 버튼을 끈다. 앱 온보딩은 홈 진입을 가로막지만 온보딩 안의 로그아웃은 가능하다. 웹은 강제 온보딩을 제거했다.

**보완 제안:** 모바일 `LLMS.md` 항목 41의 결정 대기 상태를 유지하며 선택적 등록으로 바꾸는 방향을 권장한다. 계좌가 없어도 홈, 설정, 알림, 로그아웃을 허용하고 입금·이체에 필요한 순간 등록으로 연결한다. 노란 메뉴나 별도 문구의 채택은 아직 결정된 것으로 쓰지 않는다.

계좌 60개 제한은 만들기 버튼과 서버 거절 안내에 반영한다. 마지막 계좌 삭제 후에도 앱 사용이 막히지 않게 한다. 서버가 잔액 부족이 아닌 계좌 삭제·접근 권한 문제를 답하면 목록을 다시 읽고 선택을 해제한다. 삭제 중 중복 조작을 막고 오류 상태도 계정별로 초기화한다.

**완료 조건:** 계좌 조회 실패를 “계좌 0개”로 표시하지 않는다. 삭제가 거절되면 계좌와 이유가 남는다. 활성 계좌 60개에서 추가하려 하면 한국어 안내가 나온다. 다른 곳에서 이미 삭제된 계좌를 고른 폼은 재조회 뒤 정상 선택으로 복구된다.

근거: W `apps/web/src/containers/PrivateRoutesContainer.tsx`, `apps/api/src/bankaccount-db.ts`; M `core/app_gate.dart`, `core/router.dart`, `features/onboarding/onboarding_page.dart`, `features/bank_accounts/`.

## 입금

**현재:** 내 계좌 선택, 정수 달러 검사, 서버 승인 대기, 계좌·합계·입출금 이력·거래 목록 갱신이 구현되어 있다.

**확인된 차이:** 입금 중에도 취소 버튼이 활성화되어 있고 `showDialog`의 바깥 탭 닫기가 허용된다. 성공 뒤 저장한 Navigator로 pop하므로 창을 먼저 닫은 상황에서는 다른 화면에 영향을 줄 위험이 있다. 실제 경로별 재현이 필요하다.

**보완:** 처리 중 취소, 바깥 탭, 시스템 뒤로 가기에 일관된 규칙을 적용한다. 서버로 전송한 뒤 화면을 닫아도 요청이 취소됐다고 표시하지 않는다. 성공 결과와 잔액 재조회 결과를 나누고, 재조회만 실패했을 때 입금을 다시 실행하지 않는다. 결과 불명은 [서버 계약](01-server-contract.md)의 정책을 따른다.

**완료 조건:** 처리 중 창을 닫거나 백그라운드로 갔다 돌아와도 중복 입금, 다른 화면의 잘못된 닫힘, 중단된 위젯 접근이 없어야 한다. 서버 성공 후 잔액 조회가 실패하면 “입금 완료, 잔액 갱신 필요”를 구분해서 보여 준다. 잔액 한도 초과와 삭제 계좌는 폼 안에서 이유를 확인할 수 있다.

근거: M `features/bank_transfers/deposit_dialog.dart`, `core/error_text.dart`.

## 이체

**현재:** 상대 검색, 내 계좌와 상대 계좌 선택, 잔액 부족 안내, 기본 공개 범위 적용, 비밀번호 확인, 서버 승인 후 완료 전환이 있다. 확인 창의 `_busy`는 연속 제출을 막는다.

**보완:** 403을 모두 비밀번호 오류로 바꾸지 않는다. 상대 계좌가 삭제되었거나 내 잔액이 바뀌면 계좌 목록을 갱신하고 재선택하게 한다. 비밀번호 검사 성공 직후 이체가 실패할 수 있으므로 두 단계를 구분한다. 확인 창의 시스템 뒤로 가기와 송신 후 화면 이탈도 처리해야 한다.

현재 `CreateTransactionController.submit()`은 승인 뒤 완료 상태를 먼저 쓰고 계좌와 사용자 정보를 다시 읽는다. 이후 갱신의 실패·로그아웃과 경합하는 경우에도 승인된 거래를 실패나 미전송으로 되돌리지 않도록 정리한다. 조회 실패 때문에 같은 이체를 재전송하지 않는다.

**완료 조건:** 내 잔액이 미리 보인 값보다 줄어도 서버 거절을 설명하고 다시 선택할 수 있다. 상대 계좌가 없으면 제출을 막고 상대를 바꿀 수 있다. 비밀번호 확인만 성공한 상태에서는 완료 화면이 나오지 않는다. 송신 후 응답이 끊기면 결과 불명으로 표시하고 자동 재시도하지 않는다.

근거: M `features/transactions/create/create_transaction_page.dart`, `create_transaction_controller.dart`, `password_confirm_dialog.dart`; W `apps/api/src/transaction-routes.ts`, `account-money.ts`.

## 거래 목록과 필터

**현재:** 전체·내 거래 2개 탭, 날짜, 입금·출금 금액 필터, 추가 페이지 조회, 새로고침 실패 시 이전 목록 유지가 있다. 외부 입금과 내 계좌의 거래 직후 잔액을 읽는다.

**재현할 위험:** `loadMore()`는 시작 시점의 목록을 보관했다가 응답 뒤 그대로 합친다. 기다리는 중 필터 변경, 새로고침, 사용자 전환이 생기면 오래된 응답을 새 상태에 덮어쓸 수 있다. page 방식에서는 조회 사이 새 거래가 추가될 때 중복 항목도 생길 수 있다.

**보완:** 사용자 ID, 필터, 조회 세대를 확인하고 오래된 응답은 폐기한다. 거래 ID로 중복을 제거한다. 새로고침과 다음 페이지 실패를 구분하며 이미 보인 목록과 적용 조건을 유지한다. 서버가 보낸 `myAccount.balanceAfter`에는 “거래 후 잔액”이라고 표시한다.

**완료 조건:** 다음 페이지 응답을 지연한 상태에서 조건을 바꿔도 이전 조건의 거래가 끼어들지 않는다. 동일 거래가 두 번 나오지 않는다. 검색 결과 없음은 “조건에 맞는 거래 없음”과 필터 초기화, 거래 자체 없음은 기본 빈 상태로 안내한다.

비공개 이체가 내 거래에는 보이고 전체에는 보이지 않는 것은 현재 서버 목록 규칙이다. 전체에 나오지 않는다는 이유로 앱에서 비공개 거래를 합쳐 넣지 않는다. 상세 접근 권한과 목록 노출 규칙은 구분한다.

근거: M `features/transactions/transaction_feed_controller.dart`, `transaction_filters.dart`, `transaction_list_view.dart`, `transaction.dart`.

## 거래 상세와 소통

**확인된 차이:** 서버는 중복 좋아요를 409로 거절한다. 앱은 일반 실패만 보여 주고 API·모델·상세 주석은 아직 서버가 중복을 허용한다고 설명한다. 상세 404도 일시적인 조회 실패와 같은 재시도 화면이다.

**보완:** 중복 좋아요는 “이미 좋아요를 눌렀습니다”와 최신 상태 조회로 복구한다. 접근 불가 거래는 목록 복귀를 제공한다. 댓글 전송 실패 시 초안 유지 동작은 유지하되, 응답 손실 뒤 무조건 재전송을 권하지 않는다. 상세 캐시와 진행 중 작업은 사용자 전환 때 정리한다.

외부 입금의 좋아요·댓글은 모바일 `LLMS.md` 항목 33에서 결정 대기다. 웹 목록은 소통 숫자를 숨기지만 웹 상세는 관련 UI가 있다. 숨김 여부를 “웹에서 모두 제거 완료”라고 가정하지 않는다.

**완료 조건:** 다른 기기에서 먼저 좋아요를 누른 뒤 앱에서 눌러도 오류 상태에 머물지 않는다. 404 화면에서 홈으로 돌아갈 수 있다. 새 계정으로 넘어가면 이전 계정에서 보던 비공개 상세와 댓글 초안이 남지 않는다.

근거: W `apps/api/src/social-db.ts`, `apps/web/src/components/TransactionItem.tsx`, `TransactionDetail.tsx`; M `core/api_client.dart`, `features/transactions/transaction.dart`, `transaction_detail_page.dart`.

## 알림과 잔액 갱신

**현재:** 포그라운드 SSE, 연결 때 미읽음 목록 보충, 5초 재연결, 3회 연속 실패 후 10초 조회, 백그라운드 중지, 새 받은 돈 알림에 잔액 갱신 안내가 있다. 웹은 현재 10초 조회이므로 앱을 같은 방식으로 되돌릴 필요가 없다.

**확인된 차이:** `refreshMoney()`는 조회 전에 안내를 지운다. `refreshUser()`는 실패를 숨기고 계좌 reload도 AsyncValue에 오류를 담아 정상 반환하기 때문에 모두 최신화됐는지 호출자가 알기 어렵다. SSE의 401도 다른 연결 실패처럼 재시도한다.

**보완:** 갱신 결과를 자원별로 반환하고 모두 성공한 뒤 안내를 지운다. 일부 실패면 성공한 결과는 반영하면서 실패 항목의 조회만 다시 제공한다. 알림을 이미 읽은 웹 세션이 있으면 미읽음 목록만으로 모든 잔액 변경을 알 수 없으므로 앱 복귀 때 사용자·계좌 잔액을 재조회한다. 내 다른 기기의 입금·이체도 함께 다룬다.

**완료 조건:** 안내 새로고침 중 오프라인이 되면 안내나 실패 상태가 남는다. 새로고침 연타가 겹치지 않는다. 세션이 만료되면 SSE와 폴링이 종료된다. 실제 프록시의 heartbeat 유지, 장시간 연결, Wi-Fi와 모바일 망 전환은 기기에서 확인한다.

근거: W `apps/web/src/containers/PrivateRoutesContainer.tsx`, `apps/api/src/notification-stream.ts`; M `features/notifications/notification_live_sync.dart`, `notifications_controller.dart`, `features/shell/home_shell.dart`.

## 사용자 설정과 이전 데이터

**현재:** 이메일·전화 빈 값 저장, 기본 공개 범위 선택, 저장 결과 고정 위치 표시가 있다. 서버는 변경 없음도 204로 승인한다.

**확인된 차이:** 예전 기본 공개 범위 `contacts`를 설정과 이체 컨트롤러가 `public`으로 대체한다. 옛 거래를 당사자만 볼 수 있게 하는 서버 정책과 비교하면, 다음 이체의 공개 범위가 사용자의 기대보다 넓어질 수 있다. 공개 범위 칩 변경은 Form의 입력 변경과 별개라 이전 저장 결과가 남을 가능성도 확인해야 한다.

**보완 제안:** 예전 값은 비공개 또는 재선택으로 처리하는 정책을 정한다. 설정의 이름 순서는 항목 33의 결정 대기를 유지한다. 저장 승인 후 프로필 재조회 실패는 “설정 저장 성공, 표시 정보 갱신 필요”로 구분한다. 편집 중 이전 성공 문구를 지우고 긴 실패 문구를 모두 읽게 한다.

**완료 조건:** 연락처를 비워 저장하면 재진입 후 빈 값이다. `contacts` 사용자가 별도 선택 없이 공개 이체를 만들지 않는 정책을 확정하고 적용한다. 401과 서버 장애를 “입력한 내용을 확인해 주세요”로만 안내하지 않는다.

근거: M `features/settings/settings_page.dart`, `features/transactions/create/create_transaction_controller.dart`; W `apps/api/src/user-routes.ts`, `access.ts`.

## 기존 문서 정리

모바일 README 홈 소개에는 친구 탭, 새 거래 버튼, 결제와 요청 등 현재 코드와 다른 설명이 있다. `LLMS.md`와 코드 주석에도 이전 서버 설명이 남아 있다. 기능 변경 뒤 README의 화면 소개와 이미지를 실제 화면에 맞추고, 오래된 API 주석을 정리한다. `LLMS.md` 자체 편집은 그 파일의 사용자 허가 규칙을 따른다. 현재 사용자가 수정 중인 README는 덮어쓰지 않는다.

본문 M 경로의 `core/`와 `features/`는 모두 `apps/mobile/lib/` 아래다.
